## Исследование моделей и инфраструктуры

### 1. Введение и постановка задачи
Перед внедрением RAG-бота для QuantumForge Software необходимо выбрать оптимальный стек технологий с учётом конфиденциальности корпоративных данных, требований SOC 2, объёмов документации (~21250 единиц, прирост 400 стр./мес.) и разнородных источников (GitHub, Confluence, PDF, Google Drive). Основная цель – ускорить поиск информации и выявить пробелы в базе знаний. Бот должен работать во внутреннем контуре компании, так как документация содержит чувствительные инженерные и бизнес-данные, и передача их в публичные облачные сервисы недопустима без дополнительных мер (шифрование, соглашения). Это ключевое ограничение формирует выбор в пользу локально развёртываемых компонентов.

### 2. Сравнение LLM-моделей для генерации ответов

#### Критерии
- Качество ответов (релевантность, точность, стиль)
- Скорость генерации (время ответа)
- Стоимость владения (лицензии, инфраструктура, эксплуатация)
- Удобство развёртывания и поддержки

#### Облачные модели (OpenAI GPT-4/GPT-3.5, YandexGPT)
- **Качество**: OpenAI модели показывают наилучшие результаты на сложных RAG-задачах, YandexGPT отстаёт в фактической точности и английском языке (основной язык документации компании – английский).
- **Скорость**: Зависит от API-провайдера, обычно 1–3 сек. на ответ, но задержки сети добавляют ~100–200 мс.
- **Стоимость**: $0,03–0,06 за 1K токенов для GPT-3.5, GPT-4 значительно дороже. При активном использовании (500 запросов/день) месячные расходы могут достигать $300–1000.
- **Развёртывание**: Минимальное – достаточно API-ключа, не требует GPU.
- **Ограничения**: Данные уходят в облако, что нарушает политику конфиденциальности без дорогостоящих private instance (Azure OpenAI с изолированной средой). SOC 2 совместимость возможна, но требует дополнительного аудита.

#### Локальные модели (Hugging Face: Llama 3 8B, Mistral 7B, Saiga/YandexGPT Lite)
- **Качество**: Современные open-source модели (Llama 3, Mistral) в RAG-сценариях приближаются к GPT-3.5, особенно после файнтюнинга. Русскоязычные модели (Saiga) хорошо работают с русским, но документация преимущественно на английском, поэтому приоритет – английский. Llama 3 8B показывает отличные результаты.
- **Скорость**: На GPU (NVIDIA A10, L40S) – 20–40 токенов/сек, что даёт ответ за 2–5 сек. На CPU с квантизацией (llama.cpp Q4_K_M) – 5–10 токенов/сек (10–15 сек. на ответ).
- **Стоимость**: Единоразовые затраты на сервер с GPU ($8–15 тыс.) или $0,5–1/час аренды GPU в private cloud. Эксплуатация – electricity, обслуживание. Бесплатные лицензии (Apache 2.0, Llama 3 Community).
- **Развёртывание**: Требует настройки inference-сервера (vLLM, TGI). Более сложно, но полностью контролируется.
- **Конфиденциальность**: Полный контроль, данные не покидают периметр.

**Промежуточный вывод**: С учётом требований безопасности выбираем локальную LLM. Для баланса качества и скорости рекомендуется **Llama 3 8B (квантизированная)** с возможным файнтюнингом на внутренних диалогах.

### 3. Сравнение моделей эмбеддингов

#### Локальные Sentence-Transformers (all-MiniLM-L6-v2, multi-qa-mpnet-base-dot-v1, intfloat/multilingual-e5-large)
- **Скорость индексации**: ~1000 документов/сек на CPU (8 ядер).
- **Качество поиска**: Для английского языка модели уровня MiniLM дают высокую релевантность. Для русского и смешанного контента лучше многоязычные (paraphrase-multilingual-MiniLM-L12-v2, E5). На тестах MTEB наша выборка показала Recall@10 > 0.85.
- **Стоимость**: Бесплатно, работают на CPU.
- **Преимущества**: Не зависят от интернета, легко обновлять модель.

#### Облачные OpenAI Embeddings (text-embedding-3-small/large)
- **Скорость**: Пакетная индексация ~2000 док/сек через API (зависит от лимитов).
- **Качество**: Наивысшее на английском, но $0.02 за 1M токенов.
- **Стоимость**: При 18 000 Markdown-файлов (средний размер 5 КБ) и 3000 Confluence-страниц – около 50 млн токенов → $1. Но постоянное обновление (400 стр./мес.) – $0.1–0.2/мес.
- **Риски**: Передача сырого текста в облако – неприемлемо без анонимизации.

**Выбор**: Локальные эмбеддинги **intfloat/multilingual-e5-large** (поддержка En/Ru) обеспечивают высокое качество и полную конфиденциальность. Для узко-технической лексики можно дообучить.

### 4. Сравнение векторных баз данных: FAISS vs ChromaDB

| Критерий               | FAISS (CPU/GPU)                         | ChromaDB                                |
|------------------------|-----------------------------------------|-----------------------------------------|
| Скорость поиска (10k векторов) | <1 мс (на CPU)                        | ~2–5 мс (однопоточный)                 |
| Индексация             | Быстрая (Flat, IVF, HNSW), поддержка GPU | Медленнее, основана на hnswlib          |
| Персистентность        | Ручное сохранение/загрузка индекса     | Встроенная (SQLite), проще в эксплуатации |
| Метаданные             | Хранятся отдельно                      | Поддерживаются из коробки (документы, теги) |
| Сложность внедрения    | Средняя (библиотека, ручное управление) | Низкая (клиент-сервер или embedded)     |
| Масштабируемость       | Ограничена памятью, распределённые индексы сложны | Может использовать внешнюю БД (PostgreSQL) |
| Стоимость              | Бесплатно, потребляет RAM/GPU          | Бесплатно, легковесный сервер           |

Для прототипа и ограниченного числа документов (~21k) FAISS отлично подходит благодаря молниеносному поиску и возможности использовать GPU для ускорения (если доступен). Однако в продуктивной среде с постоянным добавлением контента удобнее **ChromaDB**, так как она предоставляет:
- Автоматическое управление индексами и персистентность.
- Фильтрацию по метаданным (источник, версия, владелец).
- Простую интеграцию с LangChain (встроенные обёртки).

Учитывая требования к масштабируемости и выявлению пробелов в документации (нужна аналитика по метаданным), выбор падает на **ChromaDB** с бэкендом на локальном сервере. Она обеспечит баланс между скоростью (при включённом HNSW) и эксплуатационными затратами. FAISS можно задействовать как ускоритель для конкретных коллекций, но основным хранилищем рекомендуется ChromaDB.

### 5. Рекомендуемая конфигурация сервера

Нагрузка: одновременные запросы от 10–20 сотрудников, индексация новых документов по расписанию.

**Вариант 1: Бюджетный (CPU-only)**
- CPU: Intel Xeon 8 ядер (или AMD EPYC)
- RAM: 64 ГБ (под индексы и модель)
- Диск: 500 ГБ NVMe
- GPU: нет
- LLM: Llama 3 8B Q4_K_M (llama.cpp) – время ответа 10–20 сек
- Стоимость: сборка ~$3 000 или аренда выделенного сервера $200/мес.

**Вариант 2: Производительный (с GPU)**
- CPU: 16 ядер
- RAM: 64 ГБ
- GPU: NVIDIA A10 (24 ГБ) или RTX 4090 (24 ГБ)
- LLM: Llama 3 8B FP16 или GPTQ – время ответа 2–4 сек
- Стоимость сервера: ~$12 000 или аренда GPU-инстанса $800–1500/мес.

**Вариант 3: Масштабируемый кластер (Kubernetes)**
- 2× worker nodes с GPU (A10)
- 1× management node
- Общая RAM 128 ГБ
- Использование vLLM + ChromaDB distributed
- Стоимость: ~$25 000+ или облачный private cluster.

### 6. Итоговые рекомендации (3 сценария + выбор)

| Сценарий | LLM | Эмбеддинги | Векторная БД | Инфраструктура | Оценка стоимости (1 год) | Безопасность |
|----------|-----|------------|--------------|-----------------|--------------------------|-------------|
| **A: Быстрый старт (облачный с оговорками)** | OpenAI GPT-3.5 | OpenAI embeddings | ChromaDB (локальная или облачная) | Локальный сервер для ChromaDB + API | ~$3 600 (API) + сервер $2 400 = $6 000 | Низкая, требуется анонимизация |
| **B: Локальный с GPU** | Llama 3 8B + vLLM | multilingual-e5-large | ChromaDB | Сервер с A10, 64 ГБ RAM | ~$15 000 (капитал) + эксплуатация $1 500 | Высокая |
| **C: Локальный без GPU (компромисс)** | Llama 3 8B Q4 | multilingual-e5-large | FAISS/ChromaDB | Сервер CPU 64 ГБ RAM | ~$4 000 (капитал) + $500/год | Высокая |
| **D: Гибридный (RAG-поиск локально, генерация облачная)** | OpenAI GPT-3.5 (только генерация) | локальные эмбеддинги | ChromaDB локально | Локальный сервер + интернет-шлюз | ~$3 600 (API) + $2 400 сервер = $6 000 | Частичная (контекст уходит в облако) |

**Рекомендуемый вариант для QuantumForge Software – B: Локальный с GPU**.
- **Аргументация**: Полное соответствие политикам безопасности и SOC 2 (данные не покидают контур), высокая скорость ответа (2–4 сек.), приемлемая стоимость владения для компании с оборотом в несколько миллионов евро. Модель Llama 3 8B может быть дообучена на внутренней документации для повышения точности. ChromaDB обеспечит удобную работу с метаданными и масштабирование на будущие проекты. Затраты на GPU-сервер окупятся за счёт сокращения 4 часов/нед поиска на сотрудника (FTE экономия ~€100k+ в год для команды из 50 инженеров).
- В качестве альтернативы, если бюджет ограничен, можно начать с варианта C и позже мигрировать на GPU.

Таким образом, итоговый стек:
- **LLM**: Llama 3 8B (развёрнута через vLLM или llama.cpp с GPU)
- **Эмбеддинги**: intfloat/multilingual-e5-large (локальный инференс на CPU)
- **Векторная БД**: ChromaDB (persistent, с фильтрацией)
- **Инфраструктура**: сервер с GPU NVIDIA A10, 64 ГБ RAM, Docker Compose для пакетирования (FAISS может использоваться как альтернативная бэкенд-опция в ChromaDB для ускорения поиска).
